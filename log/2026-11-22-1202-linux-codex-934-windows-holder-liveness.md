Likely cause: Windows `process_identity` is unsupported, so `holder()` calls `process_exists(pid)`, which uses `process_name` and treats every unexpected query error as alive. The test calls `Child::wait` but retains the process handle in `kids`; a terminated Windows process object is signalled and can outlive execution while another handle stays open. Keep that handle in the regression and surface the last `InstallError` first: if it is InProgress after the OS lock is taken, use a zero-time wait on a Windows process handle with SYNCHRONIZE for liveness; WAIT_OBJECT_0 proves exit, while access denied and other indeterminate errors stay conservative. Falling back to just dropping the Child would miss the production case (e.g. a process viewer keeping a handle). The hypothesis needs a native check before calling it confirmed.
