**#895 (Node EPERM) — root cause found.**
- Node 26 `child_process.spawnSync('cmd.exe', …)` by stdio: `ignore` ok, `inherit` ok, `detached`+`ignore` ok; **`pipe` and
  `['ignore','pipe','ignore']` → EPERM**. So process creation works; libuv's stdio pipes do not.
- A pipe probe (C#) in the same agent: anonymous `CreatePipe` ok; `CreateNamedPipe` server end ok (also with `WRITE_DAC`/
  `WRITE_OWNER`), but **opening the client end by name for writing → error 5** in every variant; read-only client open → ok.
- The pipe's descriptor (no SA given, which is what libuv does): `O:<user> D:(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;<user>)(A;;FR;;;WD)
  (A;;FR;;;AN) S:(ML;;NW;;;LW)`. It is Windows' fixed default for named pipes, not the token's default DACL. The Low label is
  there, so integrity is not the problem: with `D:(A;;GA;;;WD)` (and also with a Low label added) the same open works.
- So it is the restricted-token rule: the second check sees only the restricting SIDs (agent SID, Everyone, Users, logon SID),
  and the default pipe DACL gives them only Everyone:read. libuv opens its child-side pipe end by name, so it is refused.
- Dead end checked: making the logon SID the token's default owner (the DACL gives the owner full access) → error 1307
  (invalid owner); the agent SID cannot be an owner either.
- Consequence: under the current design (restricted token + restricting SIDs) a confined Node/libuv program cannot start a child
  with piped stdio, which is how Claude Code/Gemini CLI run tools and MCP servers. Not fixable from the node side without changing
  the confinement mechanism (e.g. an AppContainer/LowBox token, or no restricting SIDs + Low label + explicit denies): that is an
  ADR-0050 decision for the maintainer, not a patch.
- Side finding: Node resolving `x.js` walks up for `package.json`; in a worktree under the user profile without one of its own
  it reaches `C:\Users\<user>\package.json`, gets EPERM and stops ("Cannot read package config … operation not permitted").
  Real JS projects have their own package.json, so this is minor; `.cjs` avoids it.

**#898 item 3 (Rust) — works:** a Rust (std, 1.99.1) probe in the same agent starts `cmd /c exit 0` with stdout `null`, `inherit`
and `piped`: all ok. So Rust agents (Codex) can run tools confined; libuv is the exception.

**Proposal:** one small PR for #898 + #895's docs part (after #830's slot): (1) sandbox docs: Node-based agents cannot start
tools/MCP servers when confined on Windows (with the reason above), Rust agents and the shell can; a confined dev server cannot share
a port with a wildcard listener; (2) the System32 read-grant log line: skip the grant for paths every user can already read (or log
it once). #895 itself stays open for the ADR decision. Say if you prefer otherwise.
