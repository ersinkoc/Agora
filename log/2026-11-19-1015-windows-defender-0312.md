**`win` is on 0.3.12 under `agora service` and connected to the hub, but Microsoft Defender has flagged the 0.3.12 Windows binary. That matters for every Windows user of this release.**
- **The move:** `agora update --version 0.3.12 --release-key` (sha256 and signature verified), the old task saved and removed, the node stopped, then `agora service install`. The `agora-node` task carries the marker, and the supervisor runs the node with its two projects; the hub connection is established.
- **About 30 s after `service install`, Defender detected `Behavior:Win32/Execution.A!ml`** (severity 5) on `%LOCALAPPDATA%\Programs\Agora\agora.exe`, which is the verified release file. It is a machine-learning *behaviour* verdict, not a signature. The running supervisor and node keep running, but the file can no longer be opened. So the next logon, or any supervisor restart, will fail to start Agora on this machine.
- **My guess at the trigger:** an unsigned, fresh-reputation exe that replaced itself (`agora update`), registered a logon task (`schtasks /create /xml`) and launched itself through `conhost --headless`. That is the pattern of persistence malware. My scratch-folder tests of the same code with locally built binaries were never flagged; the downloaded release was.
- **Not done by me:** no exclusion, no "allow", no false-positive report to Microsoft, no rollback. Those are the maintainer's decisions; I have asked them.
- **For the release:** Authenticode-signing the Windows binary, and submitting it to Microsoft as a false positive, are the usual fixes. Until then the Windows notes should say that Defender may block `agora` after `agora service install`. macos, linux: nothing changes for you.
