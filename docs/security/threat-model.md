# Threat model

Agora gives one place the power to run code-executing agents on many machines. That makes it a high-value
target. This document lists assets, trust boundaries, threats, and required mitigations. Review it in every
phase exit.

## Assets

| Asset | Where |
| --- | --- |
| Ability to execute code on machines | nodes |
| Source code and uncommitted work | nodes (checkouts, worktrees) |
| Agent and API credentials | nodes only |
| Terminal output (may contain secrets) | nodes; streamed through hub |
| Coordination data, approvals, audit log | hub |
| User and device keys | client devices, nodes |

## Trust boundaries

1. Client device ↔ hub (network)
2. Hub ↔ node (network)
3. Node ↔ agent process (local; the agent is powerful but semi-trusted)
4. Agent ↔ agent via mesh (agent output is untrusted input to another agent)
5. Node ↔ adapter/manifest packages from the registry (third-party code)
6. Agent ↔ content it reads (repos, web pages, issues): prompt-injection source

## Threats and mitigations

| # | Threat | Mitigation |
| --- | --- | --- |
| T1 | Hub compromise → commands to all nodes | Node-local policy; sensitive actions require user-signed approvals verified on the node (ADR-0020). Approvals cover what an agent asks to do (`approval_required`); the commands a hub or client routes to a node are covered by user-signed grants (ADR-0041): a node whose policy lists `signed_commands` (for example `agent.start, terminal.input, files.write`) refuses those commands with `approval.grant_required` unless a grant signed by a trusted device, for that node, scope and time, is live; the hub cannot forge one. **Open until the owner sets the line:** without a `signed_commands` line the node keeps today's behaviour and a compromised hub can still start and drive agents (found by the Codex review of 2026-11-09, `docs/reviews/2026-11-09-codex-security-surfaces.md`); a later ADR may flip the default |
| T2 | Stolen client session | Passkeys (WebAuthn, hub stores public keys only; a one-time code remains the first sign-in); a screen password for sign-ins from other machines (T17); "Lock" ends a window's session and an optional idle lock hides it; changing the password signs out every other session; 12-hour sessions stored hashed; device-bound keys; approvals require device signature |
| T3 | Rogue node enrollment | One-time enrollment codes, user confirmation in window, mTLS, revocation (ADR-0015); enrolling again under a name revokes the earlier certificate for it (one live identity per node id) and live connections are re-checked every 10 s, so a revoked node, an expired session or "sign out everywhere" ends the connection that is already open |
| T4 | Cross-agent prompt injection over mesh (agent A tells agent B to exfiltrate or delete) | Messages marked untrusted with provenance; standing instruction to agents; approvals unaffected by mesh content; rate limits |
| T5 | Prompt injection from repository content causing destructive commands | Approval policies per node/project; deny-lists for destructive commands; worktree isolation limits blast radius |
| T6 | Malicious adapter or manifest | Signed packages, pinned publisher keys, user approval to install, private registry option (ADR-0018) |
| T7 | Secret leakage via terminal streams or logs | Secrets never sent to hub; optional E2E terminal encryption; log redaction; scrollback persistence off by default |
| T8 | Agent escapes its worktree | Not prevented by default. Opt-in confinement (ADR-0047): the node's `<data>/policy` line `sandbox = worktree` starts agents (L1 terminals and the adapter process of L2/L3 agents, which carries the agent it hosts) under Linux Landlock or macOS Seatbelt (`sandbox-exec`; writes are denied outside the listed folders and file contents below `/Users`, `/Volumes` and the temp folders unless listed; the system stays readable, file names stay visible; a listed folder that holds a private one, such as `/var`, does not reopen it) so they write only in their worktree, its git folders, `/tmp` and (macOS, Windows) a temp folder of their own (plus `sandbox.write = a, b`; `~/` allowed, relative paths dropped), and read only the system, their program's folder and `sandbox.read = a, b`; `NO_NEW_PRIVS` is set. A machine that cannot enforce it (no Landlock and no `sandbox-exec`, Windows, `worktree-offline` where it has no network rules: Linux and Windows today) answers `agent.sandbox_unavailable` and starts nothing. On macOS `worktree-offline` also cuts the network: only this machine (`localhost`) and the agent's own mesh socket and private temp folder's unix sockets stay reachable, and the agent cannot listen on a TCP port. `localhost` means anything listening on this machine: a local proxy, an SSH tunnel, a DNS forwarder or a hub on the same machine is reachable too, so offline is only as closed as what runs locally. A typo in the value is the strictest level. Reduces what a confused agent can touch; it is not a promise that untrusted code is safe. A manifest's `[sandbox]` requests count only for kinds listed in `sandbox.trust_manifest`. Adapter agents also need their program and state folders listed in `sandbox.read`/`sandbox.write`. Windows (ADR-0050 with Amendment B, off until enabled): a restricted token with a per-agent SID **at Low integrity**, with a Low label on exactly the folders the agent may write, so writes anywhere else are refused whatever their ACL grants; a folder the agent would be given that lets `Users` or `Everyone` write (itself or anything below it) is refused before start (`agent.sandbox_unavailable`, `reason = broad_write_grant`), and so is one whose label the user cannot set (`reason = label_failed`, the default ACL of a data volume); a confined agent's own process and threads can be opened by the user and that agent only, not by another confined agent; reads are weaker than on Linux and macOS: files that grant `Users` or `Everyone` read stay readable, user-private files and another agent's folders are refused; the shared Git folder is read-only apart from `objects/`, `refs/` and `logs/refs/`, so an agent can add objects and move branch refs but not plant a hook or config in a worktree's main checkout; each agent's mesh endpoint admits only that agent's identity, so one confined agent cannot speak on another's connection. **msys programs (`sh`, `bash`, Git Bash) cannot start under it** (they create a kernel object directory a Low process may not create), so a tool that needs them, such as Claude Code's shell tool on Windows, does not work confined. A launch in a selected folder (ADR-0052) is refused under a confined policy when the folder is a filesystem root, the home folder or one that contains it, a secret folder below it or one that contains a secret folder (such as `~/.config`), or the node's own folder. On macOS too the shared Git folder is read-only apart from `objects/`, `refs/`, `logs/refs/` and `packed-refs`; on both, the node opens a worktree's Git folders only when `<common>/worktrees/<name>/gitdir` points back at that worktree and its `.git` is a plain file (a link to another worktree's `.git` would satisfy that check), so an agent that rewrites or replaces its `.git` file cannot make another folder writable on the next start. Not covered: another agent in the same worktree swapping the file during the instant the node reads it. Not done yet: Windows adapter commands, network rules on Linux and Windows, manifest-named hosts, manifest-declared paths; on Linux a confined agent can still write the shared `.git/hooks` and `.git/config`; on every system an agent started in a user's own checkout (not a node-made worktree) can write that checkout's `.git` |
| T8b | The node's own git runs a program an agent planted (an agent can write the git config and hooks its worktree uses; the node's git is not confined) | Every git the node runs has `core.fsmonitor`, hooks, external diff and the attributes file switched off and diffs run with `--no-textconv` (`agora-node::git::hardened`), and every filter driver the repository's own config defines (`local`, `worktree` and their includes; `.gitattributes` + `filter.<name>.clean`/`smudge`/`process`) blanked through `GIT_CONFIG_KEY_n` (not `-c`, which a `=` in the name defeats); a name it cannot pass back (not UTF-8), or a git older than 2.31 when there is any filter to blank, makes the node's git refuse to run. The user's global and system filters (Git LFS) still run. Its `status` and `diff` pass `--ignore-submodules=dirty`, because git looks inside a submodule with that submodule's own config, whose filters this does not see: a submodule moved to another commit still shows, edits inside one do not. The filter question is asked before every command and its answer counts only as exit 0 (or 1 with nothing printed); anything else, or no answer, is a refusal. In a worktree the node made, its git is pinned (`GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE`) to the Git folders recorded when `git worktree add` returned, before any agent ran there (`agora-node::git::MADE`), so nothing the agent writes into its `.git` file or `commondir` changes what the node's git reads: not another repository, not a submodule's or separate git dir's form, and not a repository it builds inside its worktree whose back-pointer checks out (which fools any check of the files on disk). In other linked worktrees (one a restarted node did not make, which has no record) it is pinned to the folders the sandbox verifies, and a `.git` that is a link is refused. Still open: on Linux a `worktree` agent can still write the shared `.git/config` and `hooks` (Windows and macOS cannot); in a worktree without a record a rewritten `.git` is followed; a repository whose own config sets `extensions.worktreeConfig` makes git read the agent's writable `config.worktree`; and wherever the agent can write a config the node's git reads (those cases), it can add a filter between the node's question and the command (a race, narrowed to one command; `GIT_ATTR_SOURCE` would close it but also switch off LFS and line-ending attributes). Git run by the user inside the agent's worktree follows whatever the agent wrote there |
| T9 | Supply chain (our dependencies, our releases) | cargo-deny, minimal deps, reproducible builds, signed releases, signed self-updates (ADR-0019) |
| T10 | Denial of service by runaway agents or mesh loops | Resource limits per node, mesh rate limits, kill switch per project/node |
| T11 | Local privilege issues (socket accessible to other users) | Per-user sockets with owner-only permissions; named pipe security descriptors on Windows |
| T12 | A local user on an SSH-only machine reaches the hub's reverse-tunnel port (ADR-0032) | The port is loopback-only; without a valid, unrevoked client certificate the only thing possible is an enrollment attempt, which is single-use, short-lived and rate limited hub-wide; `ssh` runs with BatchMode and strict host-key checking so the hub never trusts a new host silently |
| T13 | The hub's remote install (ADR-0034) puts a malicious binary or enrollment on a machine | Only a release asset is fetched, never an upload or a script; its SHA-256 and a signature pinned by the owner (`release-key`) are checked on the machine before it is installed, and without a pinned key the command stops unless the owner passes `--unsigned` (the project's release public key, as an `allowed_signers` line, is `docs/security/release-key.pub`; copy it to `<hub dir>/release-key`); every value in the remote commands is validated; the code travels over the SSH channel only and the CA on stdin; the new node starts with default policy and no trusted devices; the command is interactive and never triggered by a web action |
| T14 | An agent is talked into starting agents (ADR-0057): injected content makes it call `agent_start` to run another agent with a harmful prompt, many agents, or one in a wider folder | Every start needs a decision signed by a trusted device and verified on the node; the request the user sees shows the asking agent, machine, kind, folder (marked when outside the asker's) and the whole first prompt, and the signature covers a hash of exactly that, so a hub cannot swap the prompt or add a grant. A grant is limited to one asking agent, one kind and one folder inside its own, at most 10 starts, and ends with that agent. Depth: a helper cannot ask unless the decision allowed it, and a helper's helper never can. 3 running helpers per agent, one waiting request, 6 attempts a minute, the node's agent limit. The helper is never confined more loosely than the asker (same folder or below, or its own worktree; a trusted manifest of another kind is refused under confinement). `agent_output` reads only the asker's own helpers. No grant for a kind without an agent integration (mesh, adapter or structured mode) or for a shell. Prompts with control or invisible characters (every format character, tags, variation selectors, fillers), a leading `!`, `/`, `#`, `&` or `$`, or a last word starting with `@` are refused, and clients show any hidden character as a visible escape; the first prompt is typed only when a fresh look at the live screen shows the kind's empty input box (`[[ready]]`), and Enter only after another fresh look still shows idle with the text typed, so a trust, permission or menu dialog is never answered by it. Every request, decision, refusal and start is in the event log and the hub's audit trail, and every helper's first prompt (granted ones included) is recorded as a message from its parent. Remaining risk: a user who approves without reading the prompt |
| T15 | The session ledger (ADR-0060) is read by another local user, or a hub resumes an agent nobody asked for, or a resume starts an agent in a folder that changed | The ledger holds folder paths, agent kinds, project ids and the agents' own session ids, never terminal contents, prompts or secrets; it is owner-only (`0600` file in a `0700` folder, an owner-only ACL on Windows) and written atomically. A session id lets someone who can already run programs as that user continue that conversation with the agent's own tool; it grants nothing the user's account does not. `agent.resume` over the hub needs a trusted device's signature over that agent id (single-use nonce, five-minute expiry), like `agent.launch`; automatic resume happens only for kinds and folders the owner listed in the node's own policy file. The node refuses a resume whose folder is gone or whose project identity changed (ADR-0052), applies the same confinement and limits as a start, never restores ADR-0059 launch options (a resumed agent asks before acting), and resumes a helper only while its parent runs, without its grants or approvals. A Codex session id is read from Codex's own session file only when exactly one new file in the agent's folder fits and no other agent waits there, so Resume never continues another person's or agent's conversation by a guess; otherwise only Start again is offered. A node that runs inside a Claude Code session leaves that session's `CLAUDECODE`/`CLAUDE_CODE_*` markers out of the agents it starts. A session id never goes on a command line unless it starts with a letter or digit and holds only `[A-Za-z0-9._-]` (at most 128; a session file's id must also be a UUID), checked where it is found or reported, when the ledger is read, and right before the argv is built, so a planted session file or ledger entry cannot add an option such as `--dangerously-bypass-approvals-and-sandbox`. Resuming continues whatever conversation history the agent tool's own session file holds: someone who can write to the user's home folder (the session files under `~/.codex`, `~/.claude`) can plant or edit that history and so steer a resumed agent. Mitigations: ids are validated as above, the Resume page shows the folder the agent resumes in, and the policy default is `ask` (nothing resumes by itself). An agent whose process outlived a killed node (recorded pid, process group and start time still match) is never resumed beside itself: Resume is refused until it is stopped, and stopping it signals only that process (its group when it leads one), never a pid whose start time, boot (Linux `boot_id`, recorded next to it) or program name (`comm`) differs from the ledger's, so a hostile ledger that copies a victim's start time still cannot aim a stop at another program. Remaining risk: a folder whose contents changed under the same identity is resumed in; a separate worktree started from a folder with a portable identity (ADR-0052 metadata, not in the worktree) is refused as changed |
| T17 | Someone who learns the window's address guesses a way in (ADR-0067: password guessing) | A sign-in from any address but loopback needs a one-time code **and**, when the owner set one, the screen password; the password is checked before the code on every such attempt (a wrong password does not spend the code, and the time taken says nothing about the code); stored as PBKDF2-HMAC-SHA256 with 600 000 rounds and a random 16-byte salt, compared in constant time, never logged or returned. Wrong codes, wrong passwords and wrong passkeys are limited per address (an IPv6 address by its /64): 5 free tries, then a minute, doubling up to an hour; codes and passwords also by a hub-wide cap (50 misses). A try counts when it starts, so many sent at once cannot slip past the count. Refusals are one answer (401) for a wrong code or a wrong password, 429 only when locked out, each after the same 250 ms. Every attempt is audited with address, browser summary and result. A passkey assertion stands in for the password on its device, so adding a passkey from another machine needs the password too (misses count the same way), and setting, changing or clearing the password removes every passkey added from another machine without it (the hub keeps the ids of passkeys added on its own machine or with the password); passkey tries never count toward, or give back, the hub-wide cap. The idle lock ends the window's session at the hub like Lock. Remaining risk: a team member signing in from elsewhere needs the owner's screen password (or a passkey); the hub's loopback exemption trusts the TCP peer. **Gate for ADR-0067 rung 4 (Cloudflare Tunnel) and any reverse proxy on the hub's machine:** it must not ship until the hub takes the real client address from the tunnel (and only from it) for the loopback exemption, the rate limits and the audit trail; until then every request through it would look like the owner at the machine and skip the password |
| T18 | Lockout as denial of service: an attacker misses on purpose to lock the owner out | The per-address lockout holds only that address. The hub-wide cap holds every other machine for up to an hour, but never the hub's own machine (loopback is limited to a one-minute lockout and never by the cap) and never a passkey sign-in, so the owner always has a way in. Locking or signing out a window ends that session only; nodes and agents are untouched |
| T13 | A node forges messages as another node's agent (ADR-0031) | The hub sets `MeshPost.origin` from the connection's certificate and overwrites the node's value; only the agent id within a node is the node's word; mesh content stays untrusted data and cannot approve anything |
| T15 | An agent is started so that it does not ask (ADR-0059): by accident, by a compromised hub adding a permission-skipping launch option, or by an agent starting a helper that way | The option is a manifest declaration (`[[launch.option]] skips_permissions = true`; a known skip flag declared otherwise fails to load), never preselected, confirmed in the window (Keep asking is the primary button). Through the hub only `AgentLaunch` may carry options and its device signature covers the option ids (`directory-action-v3`), so the hub can neither add nor remove one; the confirmed ids are a separate signed list (`directory-action-v3`, both lists length-prefixed) and the node, from its own manifest, refuses an option that skips permissions unless it is confirmed (`agent.option_unconfirmed`) and refuses any id outside `[a-z0-9-]{1,32}` (`agent.option_invalid`), so a hub that relabels an option as harmless, or advertises an id such as `skip-permissions!` or `a,b`, cannot get it signed unknowingly; windows drop such ids before offering them; a routed `AgentStart` with options is refused and a grant never covers one. The node's own policy (`skip_permissions = forbid \| allow \| confined_only`, default `allow`, an unknown value, an unknown key or an unreadable existing file = `forbid`, never set over the hub) refuses a start before anything runs (`agent.option_forbidden`); `confined_only` requires the agent's confinement (ADR-0047/0050) to be active. Helpers started with `agent_start` (ADR-0057) never get an option. Every such start is audited with the option and the agent carries a "does not ask" badge in every client for its whole life |
| T19 | A node claims that it, or another node, is online (or hides that one went away) by sending presence facts (ADR-0070) | Presence is written by the hub only, from the certificate-authenticated connection whose node id the certificate decides: `NodeLink` is produced as `hub` (a name no node certificate can carry). A node that sends a `NodeLink` is refused (`protocol.invalid_message`) and the projection and the window ignore one from any producer but `hub`. A node can still say `NodeOnline`/`NodeOffline` about itself only (its producer id is checked against its certificate); a `NodeOffline` naming another node is an older gap, unchanged here. Presence never touches agents: offline is not finished |
| T16 | **Open** (found in the ADR-0059 review, pre-existing): a confined agent reaches the node's own control socket (`control.rs` accepts any local peer that can open it) and sends commands as the owner, e.g. an unsigned `AgentStart { launch_options }`, bypassing "helpers never inherit", the confirmation and the signature | Not mitigated yet. Idea: keep the control socket out of every confined agent's profile (deny it in the sandbox, as the node's own folder is), and/or identify the peer (peer credentials / the agent's confined identity) and refuse agents; tracked as a separate task |
| T20 | A malicious or compromised hub offers a fake candidate device (its own key under the owner's device name), or dresses one up so the owner says yes to the wrong thing (ADR-0061; findings of the adversarial review of #444-#446) | The hub's device list is only a list of candidates: a node trusts a listed device only after its owner answers `y` on the machine itself (`agora node enroll`, `agora node trust --from-hub`; a non-interactive terminal is a no, and `--yes` covers only the fingerprints given on the command line). The node prints every hub-supplied name and person with control, escape, bidi and other hidden characters removed and capped at 40 characters, and prints the fingerprint on a line of its own, computed on the node from the key bytes (96 bits, SHA-256), never a string from the hub, so a name cannot erase a line or paint a fake fingerprint before `[y/N]`. A listed id that would replace a different key the node already trusts is shown as such and refused without `--replace`. Only the hub owner's own devices are offered by default; other people's devices are listed apart and trusted only with `--include-others` and their fingerprints. Every registration carries a proof of possession (the device's own signature over its id, name, key and time), verified by the hub and again by the node, so a hub cannot list a key nobody holds; an ask is signed by the asking device. Endorsements are signed by a device the node already trusts, verified there and by the hub before it stores them, bound to the new key, the machines in scope and an expiry. Remaining risk: an owner who says yes without comparing fingerprints |
| T21 | A stolen or compromised trusted device endorses more devices (an attacker's browser) to keep access after the theft; a hub replays old revocations or floods the stores | Endorsements expire (at most 90 days, renewed only by use and never beyond the endorser's own remaining trust), can be limited to some machines, chains are at most two endorsements deep, and revoking a device also removes every device it endorsed (transitively). A revocation signed by any trusted device removes a device on every machine at once and refuses its earlier endorsements; `agora node untrust ID` does the same on one machine without the hub. Each trusted entry records when its trust began (`since`); a revocation removes it only when signed at or after that, so the hub resending an old revocation on every reconnect cannot undo a later re-trust. Every endorsement and revocation a node applies or refuses is written to its own log (`<data>/device-trust.log`); every id is checked against `[A-Za-z0-9._-]{1,64}` before anything is logged and logged values are escaped, so a hub cannot forge log lines. The trusted-devices file is changed under a cross-process lock and replaced atomically, so a renewal cannot bring back a device the owner just removed. Bounds: 64 devices per person not revoked, 256 revocations per person on the hub (each signature stored once), revocations forgotten after 400 days (when every endorsement older than them has expired). Remaining risk: until the owner notices and revokes, the stolen device and the ones it endorsed can approve; a hub can withhold a revocation from nodes (untrust on the machine closes that) ADR-0049 limits hold through endorsements (review of #446): a device the policy limits to some projects (`device.<id>.projects`) can endorse only a device limited to the same projects; the limit is written into the new device's line (`projects=`) and read by the node's limits whenever the file changes, so it survives restarts. Inheritance was chosen over refusing endorsements from limited devices because a member can then add their own new browser without the owner, and gains nothing they did not have. A limited device can revoke only itself or a device whose limits are within its own (never the owner's unlimited devices). An endorsement's trust starts at the earlier of its signing time and the node's clock, so a revocation signed promptly always wins over one dated ahead; endorsements and revocations dated more than 5 minutes ahead are refused by the hub and the node, so nothing from the future is remembered or can evict the 256 kept revocations. A machine is offered only the devices of the people who may act on it (the owner, people with the owner role, and people with a grant on one of its projects), not every registered device Second review of #446: the policy can narrow an inherited limit but never widen it (a device's limit is the policy line and the inherited set together, so a limited device cannot escape by endorsing a key under an id the policy names more widely; ids are first come on the hub, so this needed no malicious hub); a renewal keeps the entry's endorser and limits and only that endorser may renew it, so a limited device cannot re-parent a wider device to itself and then revoke it; a project name the trusted-devices file cannot hold (spaces, commas) refuses the endorsement (`node.policy_denied`, rule `device.projects`) instead of losing the limit; endorsements are carried only to machines the device's person may act on, while revocations, which only narrow trust and carry nothing but ids, go to every machine that verifies them (so a machine still learns of a revocation for a device the hub has since forgotten) Third review: a device's limit also follows its endorser's limit as it is now, up the chain (policy line, inherited set and the endorser's current limit, intersected), so when the owner demotes or narrows a device the devices it endorsed follow at once, and a use no longer covered by its endorser's limits does not renew the endorsement (it runs out). Only a still-valid endorsed entry is protected from being endorsed by another device; an expired one, or one whose endorser is gone, can be endorsed afresh by any trusted device (taking that device's limits). Accepted: the per-machine filter on endorsements is applied when the hub sends them, so an endorsement for a person who is given a grant on a machine later reaches that machine when it next connects, not at once Fourth review: the hub keeps every unexpired endorsement and replays it on reconnect, so one refused while its device was valid could land once that device ran out. An expired (or orphaned) endorsed device is therefore endorsed afresh only by a device whose current limits cover what it could do before (an unlimited device needs an unlimited endorser), and only with an endorsement signed after it ran out; a limited device can thus neither squat an owner's device that expired nor then renew or revoke it. Another device's endorsement of a still-valid endorsed device is refused whatever expiry it asks for Fifth review, one rule (supersedes the special cases above for a device already endorsed here): its own endorser may renew it, also after it ran out and whatever its clock, while that endorser's current limit still covers what it was given; another endorser E may take it over (re-parent it) only if E's current effective limit covers both the device's current effective limit and its current endorser's current effective limit (a wider-or-equal holder wins, a narrower one never displaces a wider one), and only with an endorsement signed at or after the device's trust ran out (its effective expiry, or its own expiry when its chain is broken), so a kept and replayed older endorsement cannot land later. The timing part applies only to a different endorser than the device's own Sixth review: the "signed after it ran out" part compares the endorsement's start on the node's own clock (the earlier of its signing time and the node's clock), so a signer whose clock runs ahead cannot take over a device in its last minutes; and an endorsement is refused not only when the endorsed device was revoked at or after it was signed, but also when its endorser was (so an endorsement the hub kept from before its endorser was revoked does not land after the endorser is trusted again). A takeover gives the device the new endorser's limit, as a fresh endorsement does; a device limited to some projects can already revoke any device whose limit lies within its own (other members' devices in those projects included), which a takeover adds nothing to |

## Kill switch

Every client exposes "stop all agents" globally, per project, and per node. The node honors it even when
the instruction arrives without hub connectivity (local CLI).

## Implementation status: approvals (T1, T4)
`agora-node::approvals` enforces on the node: signature verified against keys the node already trusts, signed message bound to
node id, approval id and verdict (no replay on another node or request, no flipping deny to allow), 128-bit random single-use
ids, expiry, cancellation when an agent stops, and a policy that lists which actions need approval. The signature scheme sits
behind a `Verifier` trait; the scheme is ECDSA P-256 (ADR-0028, `P256Verifier`). Trusted device keys reach the node only through its owner:
`agora node trust DEVICE_ID PUBLIC_KEY_HEX` writes `<data>/trusted-devices` on the machine itself (read at start and again whenever the file changes, so trusting a browser never means restarting the node and stopping its agents; malformed
lines are skipped, never trusted), and no hub or client message can edit it. The web client keeps a non-extractable P-256 key in the browser (IndexedDB); its "This device" page shows the public key and the exact `agora node trust` command, and approvals are signed there (`apps/web/src/net/approval.ts`) and verified on the node. ADR-0061 (`agora-node::device_trust`, "Devices" in `docs/specs/protocol.md`, threats T20 and T21): `agora node enroll` and
`agora node trust --from-hub` show the hub's registered devices with fingerprints and trust them only on the owner's `y` at that
terminal (a non-interactive one is a no; `--yes` covers only the fingerprints given); a device already trusted can endorse another
(verified on the node: trusted signer, this machine in scope, at most 90 days, not revoked since, never longer than the signer's own
trust; renewed by use); a revocation signed by a trusted device, or `agora node untrust`, removes a device at once and is remembered in
`<data>/device-revocations` so an older endorsement cannot bring it back; every endorsement and revocation applied or refused is
written to `<data>/device-trust.log`. The trusted-devices file stays owner-only (written beside itself and renamed).

### Signed grants for routed commands (ADR-0041)
`agora-node::grants` gates the commands a hub routes to the node (the uplink path only; the node's own control socket is never gated).
Policy line in `<data>/policy`: `signed_commands = agent.start, terminal.*, files.write` (exact names or a prefix ending in `*`; absent or
empty means none). A listed command with no live grant is refused with `approval.grant_required` and runs nothing. A grant is made by
`GrantCreate`, signed (ES256, same trusted devices as approvals) over `agora-grant-v1 NUL node_id NUL grant_id NUL scope NUL commands NUL
expires_at_ms`; `scope` is `node`, `agent:<id>` or `project:<id>`; it lasts at most 8 hours; the node keeps grants in memory only (a
restart ends them), refuses a grant id it has seen, a wrong signer, another node's grant and an expired one. `GrantList` and `GrantRevoke`
need no signature. Commands that name a worktree or open a new terminal (`files.write`, `worktree.*`, `terminal.open`) name no agent, so only
a `node` grant covers them. Recommended for a machine that is not a throwaway: `signed_commands = agent.start, terminal.input, files.write` (reading stays free). Typos in the line cannot widen anything: an unknown name simply matches no command. Tests: `crates/agora-node/src/grants.rs` and `crates/agora/tests/hub_dial.rs`.

### Launch options that skip permissions (ADR-0059, T15)
Policy line in `<data>/policy`: `skip_permissions = forbid | allow | confined_only` (absent: `allow`, the maintainer's default; any
other value counts as `forbid`). It is read when the node starts and never changes over the hub. `agora-node::launch_options` resolves a
start's option ids against the kind's manifest (unknown, repeated or more than 8: `protocol.invalid_message`) and refuses a
`skips_permissions` option the policy does not allow with `agent.option_forbidden` before any worktree, mesh endpoint or process
exists; `confined_only` allows it only when the node confines agents (`sandbox` not `off`) and can here. Through the hub, an
`AgentLaunch` with options is verified over `directory-action-v3` (the option ids are signed); a routed `AgentStart` with options is
refused at the uplink (`policy: signature`) whatever grant is live; the hub refuses to forward options to a node without the
capability `agent.launch_options`. Helpers (`agent_start`) are started through the supervisor's option-less calls, so they never
get one. The arguments are kept for the agent's whole life (crash restarts and resumes use them too); `AgentStarted` carries the ids
and `skips_permissions`, the hub keeps them in the snapshot (the badge) and writes an audit row `agent.launch_options` for every such
start, local ones included, besides the routed command's row (`AgentLaunch[skip-permissions]`). Tests:
`crates/agora-node/tests/launch_options.rs`, `agent_spawn.rs` (`a_helper_never_inherits_a_launch_option`),
`directory_authorization.rs`, `uplink_client.rs` and `router.rs` unit tests.

### Approvals: node wiring
Adapter approval requests enter the node's queue under a random node-minted id (the adapter's own id is only used to answer it),
are announced as `ApprovalRequested`, and wait. `approval.resolve` verifies the device signature on the node and relays the verdict
to the adapter, recording `ApprovalResolved` with the signer; requests that expire are answered as denied; a stopped or crashed
agent leaves nothing waiting. With no trusted device (the default until the owner runs `agora node trust`) every decision is
refused with `approval.signature_invalid`, so sensitive actions stay denied rather than open. Adapter usage and session reports
are written to the event log.

## Team mode (ADR-0049)
A hub may have several people with a role each (`owner`, `member`, `viewer`). The hub refuses a viewer's commands that change anything (`auth.forbidden`) and checks the role on every command, so a demotion or a removal takes effect on an open connection. This is the hub's own limit on its clients and not a security boundary: a compromised hub is still bounded only by the node's policy and signed grants (ADR-0020, ADR-0041). A member or viewer sees only the projects granted to them: the hub cuts their snapshot, forwards only their events, and refuses commands that do not name something in a granted project (`agora_hub::scope`). On the node, `device.<id>.projects = a, b` in `<data>/policy` limits what a trusted device may sign: grants only scoped to those projects (never `node`), and approvals only for agents of those projects; a device the file does not name is limited by nothing (today's behaviour), and a named one with no projects acts in none. The hub cannot change the file. When a node names any limited device and has no `signed_commands` line, it requires a grant for every command that changes something (`agent.start|stop|prompt|set_mode`, `terminal.open|input`, `files.write`, `worktree.create|remove`), so the limits bind those commands; a limited device can only sign project or agent grants, so whole-machine commands (`terminal.open`, `files.write`, `worktree.*`) stay the owner's. An owner who writes a `signed_commands` line decides the list. Without limited devices nothing changes. This binds only what is signed: the commands a node lists in `signed_commands` need a grant, so a member's browser device is limited by the node only for those commands (an owner who wants a member limited on the machine lists the commands there). Commands outside `signed_commands` still rely on the hub's role and project checks. The audit trail itself exists (`agora hub audit export`): every routed command, sign-in and change to the team is a row, kept by database triggers that refuse deletes and edits, so a client command cannot rewrite history; a compromised hub process with database access still can, so the trail is evidence about people, not about the hub.

Found by an independent audit after 0.2.0 and fixed: a passkey added by a member or viewer used to sign in as the owner (passkeys had no person, and a sign-in with one made an owner session). A passkey now belongs to the person whose session added it and signs in as that person (schema 8); removing a person removes their passkeys; the ids `owner` and `hub`, which the hub writes itself, can no longer be a person's (so no audit row can pose as the owner's); and starting an agent in an existing worktree is checked against the person's projects. Known and accepted: a member sees the machine-wide counts in a machine's resource events (agents running, terminals open, memory) for any machine that hosts one of their projects.

## Selected folders and portable identities (ADR-0052)

Directory inspection and launch are always authorized on the node by an exact-request trusted-device signature over
node, operation, path, kind, expected project, metadata/worktree option, changed-identity confirmation, nonce and expiry.
A generic start grant cannot substitute another path. Used nonces persist across restarts; malformed or full replay state
fails closed. See `specs/protocol.md` for the canonical encoding. A device limited to some projects (ADR-0049) may take
these actions only inside its projects, placed by the node's own records (folders launches confirmed and registered
checkouts, nearest wins; the session ledger for a resume), never by a folder's metadata, so a copied identity cannot move a
folder into its project; it can neither create nor change an identity, list the home folder or any folder outside its
projects, and the check runs after the signature so only a trusted device learns where a project is. Accepted: a known
folder of its project is resolved again when the action runs, so whoever can change the machine's folders between the check
and the action (a local user, not the hub) could redirect it. The local owner-only socket keeps its authority.


Folder listing (ADR-0053 `directory.list`) discloses **folder names only** (and whether each holds a `.git`), one folder per
call, at most 500, to the same exact-request owner signature (operation `list`, node and path bound, single-use nonce); a
device limited to projects never lists a machine. The node never lists a file, a link, a secret folder below the home folder
or its own folder (the same set a confined launch refuses), and refuses to list one of those when asked directly. The
decision is made on the folder the open handle holds: the path is opened once, the handle's own path must be the canonical
folder asked for, the secret-folder check runs on that path and the entries are read through that handle, so a folder
swapped for a link between two looks cannot show a secret folder (tested with a folder flipped against `~/.ssh`). The local
owner-only socket keeps its authority here as well.
The node resolves symlinks and re-inspects the canonical path/project immediately before launching. It preserves selected
user-owned folders on stop or failure. MCP files for direct L1 sessions live in separate session folders, accessible to that
agent's sandbox as read-only configuration; fixed-file-only MCP manifests require explicit worktree mode. Opt-in sandbox
policy still applies to the selected cwd. Sharing a folder deliberately shares its files; file leases cannot intercept an
agent's own shell writes, and the UI makes no per-agent attribution of a shared diff.

Repository metadata is untrusted data. It never enrolls a node, grants access, joins another owner's project or changes
device limits. It is a size-limited regular JSON file with a validated UUID. Previously confirmed path/ID bindings are
persisted and cannot silently switch after repository edits; an explicit signed owner confirmation is needed. Hub project
filters group confirmed logical IDs while preserving each machine and path; role/project filters still apply to workspace
snapshots, status events and file queries. Copying this metadata transfers identity, not source files or authorization.

Selected-directory review follow-up (#257): explicit worktree launch resolves the new root and walks the selected
relative directory without following restored symlinks. Missing directories are created only below that root; a
non-directory or symlink is refused before launch. Workspace diffs include an explicit selected-directory pathspec
even for an empty requested path, keeping parent-checkout changes outside the workspace review. Confinement tests
place a selected subdirectory outside the shared system temp folder and prove inside writes succeed while parent
checkout writes fail, in both directory and explicit-worktree modes. Explicit policy write allowances still apply.

## Open gap: unix sockets under confinement

A confined agent (`sandbox = worktree`) can connect to any unix socket it can name. A tmux server socket or `SSH_AUTH_SOCK` lets it run a command or use
credentials outside the confinement. Landlock covers this only from ABI 9; Seatbelt needs an explicit rule. Tracked as L21 in
`docs/backlog/lan-test-findings.md`; `worktree-offline` on macOS already allows only the agent's own mesh socket.
