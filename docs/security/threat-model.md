# Threat model

Agora gives one place the power to run code-executing agents on many machines. That makes it a high-value
target. This document lists assets, trust boundaries, threats, and required mitigations. Review it in every
phase exit.

## Assets

| Asset | Where |
| --- | --- |
| Ability to execute code on machines | nodes |
| Source code and uncommitted work | nodes (checkouts, worktrees) |
| Agent and API credentials | nodes only |
| Terminal output (may contain secrets) | nodes; streamed through hub |
| Coordination data, approvals, audit log | hub |
| User and device keys | client devices, nodes |

## Trust boundaries

1. Client device ↔ hub (network)
2. Hub ↔ node (network)
3. Node ↔ agent process (local; the agent is powerful but semi-trusted)
4. Agent ↔ agent via mesh (agent output is untrusted input to another agent)
5. Node ↔ adapter/manifest packages from the registry (third-party code)
6. Agent ↔ content it reads (repos, web pages, issues): prompt-injection source

## Threats and mitigations

| # | Threat | Mitigation |
| --- | --- | --- |
| T1 | Hub compromise → commands to all nodes | Node-local policy; sensitive actions require user-signed approvals verified on the node (ADR-0020). Approvals cover what an agent asks to do (`approval_required`); the commands a hub or client routes to a node are covered by user-signed grants (ADR-0041): a node whose policy lists `signed_commands` (for example `agent.start, terminal.input, files.write`) refuses those commands with `approval.grant_required` unless a grant signed by a trusted device, for that node, scope and time, is live; the hub cannot forge one. **Open until the owner sets the line:** without a `signed_commands` line the node keeps today's behaviour and a compromised hub can still start and drive agents (found by the Codex review of 2026-11-09, `docs/reviews/2026-11-09-codex-security-surfaces.md`); a later ADR may flip the default |
| T2 | Stolen client session | Passkeys (WebAuthn, hub stores public keys only; a one-time code remains the first sign-in); a screen password for sign-ins from other machines (T17); "Lock" ends a window's session and an optional idle lock hides it; changing the password signs out every other session; 12-hour sessions stored hashed; device-bound keys; approvals require device signature |
| T3 | Rogue node enrollment | One-time enrollment codes, user confirmation in window, mTLS, revocation (ADR-0015); enrolling again under a name revokes the earlier certificate for it (one live identity per node id) and live connections are re-checked every 10 s, so a revoked node, an expired session or "sign out everywhere" ends the connection that is already open |
| T4 | Cross-agent prompt injection over mesh (agent A tells agent B to exfiltrate or delete) | Messages marked untrusted with provenance; standing instruction to agents; approvals unaffected by mesh content; rate limits |
| T5 | Prompt injection from repository content causing destructive commands | Approval policies per node/project; deny-lists for destructive commands; worktree isolation limits blast radius |
| T6 | Malicious adapter or manifest | Signed packages, pinned publisher keys, user approval to install, private registry option (ADR-0018) |
| T7 | Secret leakage via terminal streams or logs | Secrets never sent to hub; optional E2E terminal encryption; log redaction; scrollback persistence off by default |
| T8 | Agent escapes its worktree | Not prevented by default. Opt-in confinement (ADR-0047): the node's `<data>/policy` line `sandbox = worktree` starts agents (L1 terminals and the adapter process of L2/L3 agents, which carries the agent it hosts) under Linux Landlock or macOS Seatbelt (`sandbox-exec`; writes are denied outside the listed folders and file contents below `/Users`, `/Volumes` and the temp folders unless listed; the system stays readable, file names stay visible; a listed folder that holds a private one, such as `/var`, does not reopen it) so they write only in their worktree, its git folders, `/tmp` and (macOS, Windows) a temp folder of their own (plus `sandbox.write = a, b`; `~/` allowed, relative paths dropped), and read only the system, their program's folder and `sandbox.read = a, b`; `NO_NEW_PRIVS` is set. On Linux, truncating a file (`truncate(2)`, `O_TRUNC`) outside the folders it may write is refused only on a kernel whose Landlock is version 3 or later (Linux 6.2); an older kernel cannot refuse it. Moving or linking a file between folders it may write needs version 2 (Linux 5.19); a file from a read-only folder can never be moved or linked into them (audit F260, F261). A machine that cannot enforce it (no Landlock and no `sandbox-exec`, Windows, `worktree-offline` where it has no network rules: Linux and Windows today) answers `agent.sandbox_unavailable` and starts nothing. On macOS `worktree-offline` also cuts the network: only this machine (`localhost`) and the unix sockets in the agent's own allow-list (its mesh socket, its worktree, its private temp folder and the owner's `sandbox.sockets`) stay reachable, and the agent cannot listen on a TCP port. `localhost` means anything listening on this machine: a local proxy, an SSH tunnel, a DNS forwarder or a hub on the same machine is reachable too, so offline is only as closed as what runs locally. On macOS preferences (`defaults`, CFPreferences) follow the same file rules although the `cfprefsd` service reads and writes them for the agent: a domain under `~/Library/Preferences` is readable or writable only when its file is listed, and the global domain (language, locale) stays readable but not writable. A typo in the value is the strictest level. Reduces what a confused agent can touch; it is not a promise that untrusted code is safe. A manifest's `[sandbox]` requests count only for kinds listed in `sandbox.trust_manifest`. Adapter agents also need their program and state folders listed in `sandbox.read`/`sandbox.write`. Windows (ADR-0050 with Amendment B, off until enabled): a restricted token with a per-agent SID **at Low integrity**, with a Low label on exactly the folders the agent may write, so writes anywhere else are refused whatever their ACL grants; a folder the agent would be given that lets `Users` or `Everyone` write (itself or anything below it) is refused before start (`agent.sandbox_unavailable`, `reason = broad_write_grant`), and so is one whose label the user cannot set (`reason = label_failed`, the default ACL of a data volume); a confined agent's own process and threads can be opened by the user and that agent only, not by another confined agent; reads are weaker than on Linux and macOS: files that grant `Users` or `Everyone` read stay readable, user-private files and another agent's folders are refused; the shared Git folder is read-only apart from `objects/`, `refs/` and `logs/refs/`, so an agent can add objects and move branch refs but not plant a hook or config in a worktree's main checkout; each agent's mesh endpoint admits only that agent's identity, so one confined agent cannot speak on another's connection. **msys programs (`sh`, `bash`, Git Bash) cannot start under it** (they create a kernel object directory a Low process may not create), so a tool that needs them, such as Claude Code's shell tool on Windows, does not work confined. A launch in a selected folder (ADR-0052) is refused under a confined policy when the folder is a filesystem root, the home folder or one that contains it, a secret folder below it or one that contains a secret folder (such as `~/.config`), or the node's own folder. On macOS too the shared Git folder is read-only apart from `objects/`, `refs/`, `logs/refs/` and `packed-refs`; on both, the node opens a worktree's Git folders only when `<common>/worktrees/<name>/gitdir` points back at that worktree and its `.git` is a plain file (a link to another worktree's `.git` would satisfy that check), so an agent that rewrites or replaces its `.git` file cannot make another folder writable on the next start. Not covered: another agent in the same worktree swapping the file during the instant the node reads it. Unix sockets (ADR-0083): a confined agent's environment does not carry `SSH_AUTH_SOCK`, `GPG_AGENT_INFO`, `DBUS_SESSION_BUS_ADDRESS`, `DOCKER_HOST`, `TMUX` or `TMUX_PANE` from the node (every system; terminal agents; adapter agents never inherit them; the owner lets one through with `sandbox.pass_env = NAME, ...`, names only), and where the system can say it the connection itself is refused: on macOS the rule that refuses every unix socket outside an allow-list is on (measured on a real Mac, macOS 27.2.1, by the macOS developer on 2026-11-17: the agent's own socket open, another closed, the name resolver open, a confined `git commit` works; the first CI failure was a profile that did not parse, a nested `subpath`, not a stall, and a test now runs every profile shape through `sandbox-exec`). NOT yet measured with real agents: the other system sockets a tool needs (DNS in every tool, git over https, cargo, npm, Claude Code, Codex under `worktree`; the allow-list holds only `/private/var/run/mDNSResponder`); on Linux with Landlock ABI 6 or newer (Linux 6.12) only abstract unix sockets made outside the agent's sandbox are (X11's abstract socket, `unix:abstract=` D-Bus). On Linux there is no Landlock right for pathname sockets in the kernel headers this was built against, so there an agent that looks for `/tmp/ssh-*/agent.*`, `/run/user/<uid>/bus`, the docker socket or a tmux socket can still connect: the variable scrub is the only layer, and `agora doctor` says so. On Windows AF_UNIX was not measured and nothing is restricted. Not done yet: Windows adapter commands, network rules on Linux and Windows, manifest-named hosts, manifest-declared paths; on Linux a confined agent can still write the shared `.git/hooks` and `.git/config`; on every system an agent started in a user's own checkout (not a node-made worktree) can write that checkout's `.git` |
| T8b | The node's own git runs a program an agent planted (an agent can write the git config and hooks its worktree uses; the node's git is not confined) | Every git the node runs has `core.fsmonitor`, hooks, external diff and the attributes file switched off and diffs run with `--no-textconv` (`agora-node::git::hardened`), and every filter driver the repository's own config defines (`local`, `worktree` and their includes; `.gitattributes` + `filter.<name>.clean`/`smudge`/`process`) blanked through `GIT_CONFIG_KEY_n` (not `-c`, which a `=` in the name defeats); a name it cannot pass back (not UTF-8), or a git older than 2.31 when there is any filter to blank, makes the node's git refuse to run. The user's global and system filters (Git LFS) still run. Its `status` and `diff` pass `--ignore-submodules=dirty`, because git looks inside a submodule with that submodule's own config, whose filters this does not see: a submodule moved to another commit still shows, edits inside one do not. The filter question is asked before every command and its answer counts only as exit 0 (or 1 with nothing printed); anything else, or no answer, is a refusal. In a worktree the node made, its git is pinned (`GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE`) to the Git folders recorded when `git worktree add` returned, before any agent ran there (`agora-node::git::MADE`), so nothing the agent writes into its `.git` file or `commondir` changes what the node's git reads: not another repository, not a submodule's or separate git dir's form, and not a repository it builds inside its worktree whose back-pointer checks out (which fools any check of the files on disk). In other linked worktrees (one a restarted node did not make, which has no record) it is pinned to the folders the sandbox verifies, and a `.git` that is a link is refused. Still open: on Linux a `worktree` agent can still write the shared `.git/config` and `hooks` (Windows and macOS cannot); in a worktree without a record a rewritten `.git` is followed; a repository whose own config sets `extensions.worktreeConfig` makes git read the agent's writable `config.worktree`; and wherever the agent can write a config the node's git reads (those cases), it can add a filter between the node's question and the command (a race, narrowed to one command; `GIT_ATTR_SOURCE` would close it but also switch off LFS and line-ending attributes). Git run by the user inside the agent's worktree follows whatever the agent wrote there |
| T9 | Supply chain (our dependencies, our releases) | cargo-deny, minimal deps, reproducible builds, signed releases, signed self-updates (ADR-0019) |
| T10 | Denial of service by runaway agents or mesh loops | Resource limits per node, mesh rate limits, kill switch per project/node |
| T11 | Local privilege issues (socket accessible to other users) | Per-user sockets with owner-only permissions; named pipe security descriptors on Windows |
| T12 | A local user on an SSH-only machine reaches the hub's reverse-tunnel port (ADR-0032) | The port is loopback-only; without a valid, unrevoked client certificate the only thing possible is an enrollment attempt, which is single-use, short-lived and rate limited hub-wide; `ssh` runs with BatchMode and strict host-key checking so the hub never trusts a new host silently |
| T13 | The hub's remote install (ADR-0034) puts a malicious binary or enrollment on a machine | Only a release asset is fetched, never an upload or a script; its SHA-256 and a signature pinned by the owner (`release-key`) are checked on the machine before it is installed, and without a pinned key the command stops unless the owner passes `--unsigned` (the project's release public key, as an `allowed_signers` line, is `docs/security/release-key.pub`; copy it to `<hub dir>/release-key`); every value in the remote commands is validated; the code travels over the SSH channel only and the CA on stdin; the new node starts with default policy and no trusted devices; the command is interactive and never triggered by a web action |
| T14 | An agent is talked into starting agents (ADR-0057): injected content makes it call `agent_start` to run another agent with a harmful prompt, many agents, or one in a wider folder | Every start needs a decision signed by a trusted device and verified on the node; the request the user sees shows the asking agent, machine, kind, folder (marked when outside the asker's) and the whole first prompt, and the signature covers a hash of exactly that, so a hub cannot swap the prompt or add a grant. A grant is limited to one asking agent, one kind and one folder inside its own, at most 10 starts, and ends with that agent. It also ends for good with the trust of the device that signed it (audit F290): before each start it would cover, and when grants are listed, the node reads the trusted-devices file again if it changed and checks the decision's signature under the devices trusted now, in the same term of trust (a device removed and trusted again starts a new one), before an endorsed device's trust runs out, and within the device's current limits; it renews nothing. Depth: a helper cannot ask unless the decision allowed it, and a helper's helper never can. 3 running helpers per agent, one waiting request, 6 attempts a minute, the node's agent limit. The helper is never confined more loosely than the asker (same folder or below, or its own worktree; a trusted manifest of another kind is refused under confinement). `agent_output` reads only the asker's own helpers. No grant for a kind without an agent integration (mesh, adapter or structured mode) or for a shell. Prompts with control or invisible characters (every format character, tags, variation selectors, fillers), a leading `!`, `/`, `#`, `&` or `$`, or a last word starting with `@` are refused, and clients show any hidden character as a visible escape; the first prompt is typed only when a fresh look at the live screen shows the kind's empty input box (`[[ready]]`), and Enter only after another fresh look still shows idle with the text typed, so a trust, permission or menu dialog is never answered by it. Every request, decision, refusal and start is in the event log and the hub's audit trail, and every helper's first prompt (granted ones included) is recorded as a message from its parent. Remaining risk: a user who approves without reading the prompt |
| T15 | The session ledger (ADR-0060) is read by another local user, or a hub resumes an agent nobody asked for, or a resume starts an agent in a folder that changed | The ledger holds folder paths, agent kinds, project ids and the agents' own session ids, never terminal contents, prompts or secrets; it is owner-only (`0600` file in a `0700` folder, an owner-only ACL on Windows) and written atomically. A session id lets someone who can already run programs as that user continue that conversation with the agent's own tool; it grants nothing the user's account does not. `agent.resume` over the hub needs a trusted device's signature over that agent id (single-use nonce, five-minute expiry), like `agent.launch`; automatic resume happens only for kinds and folders the owner listed in the node's own policy file, or for every agent when the machine's owner runs the node with `--resume auto` (ADR-0062 item 4: what `agora` passes when the owner answered yes; set on the machine itself, never by the hub; a `resume` line in the node's policy file always wins, the stricter of the two), at most 16 at one start and 8 at a time, never one brought back by itself in the last 10 minutes. The node refuses a resume whose folder is gone or whose project identity changed (ADR-0052), applies the same confinement and limits as a start, never restores ADR-0059 launch options (a resumed agent asks before acting), and resumes a helper only while its parent runs, without its grants or approvals. A Codex session id is read from Codex's own session file only when exactly one new file in the agent's folder fits and no other agent waits there, so Resume never continues another person's or agent's conversation by a guess; otherwise only Start again is offered. A node that runs inside a Claude Code session leaves that session's `CLAUDECODE`/`CLAUDE_CODE_*` markers out of the agents it starts. A session id never goes on a command line unless it starts with a letter or digit and holds only `[A-Za-z0-9._-]` (at most 128; a session file's id must also be a UUID), checked where it is found or reported, when the ledger is read, and right before the argv is built, so a planted session file or ledger entry cannot add an option such as `--dangerously-bypass-approvals-and-sandbox`. Resuming continues whatever conversation history the agent tool's own session file holds: someone who can write to the user's home folder (the session files under `~/.codex`, `~/.claude`) can plant or edit that history and so steer a resumed agent. Mitigations: ids are validated as above, the Resume page shows the folder the agent resumes in, and the policy file's default is `ask`; a machine set up with `agora` resumes by itself only after its owner answered yes (Enter, the maintainer's chosen default) to the question asked once, which `agora --resume ask --save` changes; an upgrade from a version without the question changes nothing until it is answered. An agent whose process outlived a killed node (recorded pid, process group and start time still match) is never resumed beside itself: Resume is refused until it is stopped, and stopping it signals only that process (its group when it leads one), never a pid whose start time, boot (Linux `boot_id`, recorded next to it) or program name (`comm`) differs from the ledger's, so a hostile ledger that copies a victim's start time still cannot aim a stop at another program. Remaining risk: a folder whose contents changed under the same identity is resumed in; a separate worktree started from a folder with a portable identity (ADR-0052 metadata, not in the worktree) is refused as changed |
| T17 | Someone who learns the window's address guesses a way in (ADR-0067: password guessing) | A sign-in from any address but loopback needs a one-time code **and**, when the owner set one, the screen password; the password is checked before the code on every such attempt (a wrong password does not spend the code, and the time taken says nothing about the code); stored as PBKDF2-HMAC-SHA256 with 600 000 rounds and a random 16-byte salt, compared in constant time, never logged or returned. Wrong codes, wrong passwords and wrong passkeys are limited per address (an IPv6 address by its /64): 5 free tries, then a minute, doubling up to an hour; codes and passwords also by a hub-wide cap (50 misses). A try counts when it starts, so many sent at once cannot slip past the count. Refusals are one answer (401) for a wrong code or a wrong password, 429 only when locked out, each after the same 250 ms. Every attempt is audited with address, browser summary and result. A passkey assertion stands in for the password on its device, so adding a passkey from another machine needs the password too (misses count the same way), and setting, changing or clearing the password removes every passkey added from another machine without it (the hub keeps the ids of passkeys added on its own machine or with the password; a passkey added from another machine without it under the id of a removed passkey does not inherit that passkey's place on the list); passkey tries never count toward, or give back, the hub-wide cap. The idle lock ends the window's session at the hub like Lock. Remaining risk: a team member signing in from elsewhere needs the owner's screen password (or a passkey); the hub's loopback exemption trusts the TCP peer. **Gate for ADR-0067 rung 4 (Cloudflare Tunnel) and any reverse proxy on the hub's machine:** it must not ship until the hub takes the real client address from the tunnel (and only from it) for the loopback exemption, the rate limits and the audit trail; until then every request through it would look like the owner at the machine and skip the password |
| T18 | Lockout as denial of service: an attacker misses on purpose to lock the owner out | The per-address lockout holds only that address. The hub-wide cap holds every other machine for up to an hour, but never the hub's own machine (loopback is limited to a one-minute lockout and never by the cap) and never a passkey sign-in, so the owner always has a way in. Passkey challenges (asked for without signing in) are kept per address (an IPv6 address by its /64): one address holds at most 4 waiting at once, its own oldest making room, and when the hub-wide table (256) is full the address holding the most loses its oldest, so asking for challenges from one address cannot throw away the owner's. Remaining risk: hundreds of addresses each asking at once can still fill the table: 256 or more distinct address buckets within the 5 minutes a challenge lives can still evict a waiting passkey challenge (an availability loss only: the password plus a one-time code still sign in). Locking or signing out a window ends that session only; nodes and agents are untouched |
| T13 | A node forges messages as another node's agent (ADR-0031) | The hub sets `MeshPost.origin` from the connection's certificate and overwrites the node's value; only the agent id within a node is the node's word; mesh content stays untrusted data and cannot approve anything |
| T15 | An agent is started so that it does not ask (ADR-0059): by accident, by a compromised hub adding a permission-skipping launch option, or by an agent starting a helper that way | The option is a manifest declaration (`[[launch.option]] skips_permissions = true`; a known skip flag declared otherwise fails to load), never preselected, confirmed in the window (Keep asking is the primary button). Through the hub only `AgentLaunch` may carry options and its device signature covers the option ids (`directory-action-v3`), so the hub can neither add nor remove one; the confirmed ids are a separate signed list (`directory-action-v3`, both lists length-prefixed) and the node, from its own manifest, refuses an option that skips permissions unless it is confirmed (`agent.option_unconfirmed`) and refuses any id outside `[a-z0-9-]{1,32}` (`agent.option_invalid`), so a hub that relabels an option as harmless, or advertises an id such as `skip-permissions!` or `a,b`, cannot get it signed unknowingly; windows drop such ids before offering them; a routed `AgentStart` with options is refused and a grant never covers one. The node's own policy (`skip_permissions = forbid \| allow \| confined_only`, default `allow`, an unknown value, an unknown key or an unreadable existing file = `forbid`, never set over the hub) refuses a start before anything runs (`agent.option_forbidden`); `confined_only` requires the agent's confinement (ADR-0047/0050) to be active. Helpers started with `agent_start` (ADR-0057) never get an option. Every such start is audited with the option and the agent carries a "does not ask" badge in every client for its whole life |
| T19 | A node claims that it, or another node, is online (or hides that one went away) by sending presence facts (ADR-0070) | Presence is written by the hub only, from the certificate-authenticated connection whose node id the certificate decides: `NodeLink` is produced as `hub` (a name no node certificate can carry). A node that sends a `NodeLink` is refused (`protocol.invalid_message`) and the projection and the window ignore one from any producer but `hub`. A node speaks for itself only: its producer id is checked against its certificate, and every fact that names a node (`NodeOnline`, `NodeOffline`, `NodeResources`, `CheckoutDiscovered`, `AgentStarted`, `TerminalOpened`, `WorkspaceRegistered`) must name the sender, or it is refused (`protocol.invalid_message`, field `node_id`); `NodeLink`, `NodeForgotten` and `AgentForgotten` are the hub's own and refused from any node. Besides the refusal, the hub's view takes the node id of a start, a goodbye, an agent, a terminal, a checkout and resource numbers from the connection that sent the event, never from its body (the one exception is a `NodeOffline` the hub itself wrote for an older client, which names the node whose connection ended), and ignores `AgentForgotten` from anyone but the hub; so an event stored before this check existed cannot end, hide or move anything of another node when the history is replayed (a hub restart replays the store). The same stored record is never replayed to a window either: a hub that opens over one (the `is_forged` rule, shared with live ingestion) answers every window whose position is at or before the end of the log at that moment with a snapshot, not a replay, which also heals a window that applied it before; the stored history itself is never rewritten. Presence never touches agents: offline is not finished. Known residual (integration review F5, pre-existing): the hub's projection of `TaskChanged` tasks and leases is keyed by raw ids and sits outside the node-id check (`named_node` answers no node for it), so a node can overwrite another node's task entry in the owner's view only (task events are not scoped to other users); it never reaches an agent or a node |
| T16 | **Mitigated on macOS, Windows and Linux** (found in the ADR-0059 review, pre-existing): a confined agent reaches the node's own control socket (`control.rs` accepts any local peer that can open it) and sends commands as the owner, e.g. an unsigned `AgentStart { launch_options }`, bypassing "helpers never inherit", the confirmation and the signature; or types into another agent's terminal (measured on macOS before the fix) | macOS (#475, #477 and its two security reviews): every confined agent's Seatbelt profile closes the node's **whole home** (data beside its worktrees or its control socket, as `agora node` lays it out, also with `--worktrees` elsewhere; else its data, control socket, mesh-socket folder and manifests; relative paths made absolute; never the user's home or a folder above it, nor one holding a project the node serves; a protected path that cannot be resolved refuses the start, `agent.sandbox_unavailable` reason `protected_path_unresolved`, rather than being left out) after everything it opens (the last matching rule wins), as an allow-list: its own worktree and its own mesh socket are opened again, nothing else. The worktree is opened again only while it is a real folder, checked at every start: an agent that replaced it with a link (into the home, to have it opened at its resume, or anywhere else) is refused (`worktree_not_folder`), and resume already refuses a folder whose path changed (ADR-0052), and no `read` or `write` entry that resolves into the home (an owner's `~/.claude` the agent made a link) is opened. Nor is any entry reached through a link the agent could have made (#545): a link below a place it may write, or at such a place in a folder this user may write, refuses the start (`writable_is_link`) instead of giving the agent where it points (measured: `ln -s ~/.zshrc ~/.claude.json` made `.zshrc` writable at the next start before the fix); an owner's own link outside what the agent may write (a dotfiles `~/.gitconfig`) and the system's (`/tmp` in `/`) are followed, while an owner's link at a place the agent may write (a stow-style `~/.claude -> ~/dotfiles/claude`) is refused, as it cannot be told apart from one the agent made. Each entry is walked one component at a time (`openat` with `O_NOFOLLOW`, links read with `readlinkat` and followed by hand, the end's path from `F_GETPATH`), so checking a link and resolving the entry are one step (measured before: another process flipping a write entry between a folder and a link to `~` got `~` into 455 of 3000 profiles; after: none), and places are compared where the kernel has them, so `/private/tmp`, `/System/Volumes/Data/...` and other case are the same place. Every rule names the kernel's path: Seatbelt matches that path, and a rule spelled through the `/System/Volumes/Data` firmlink matched nothing (measured: a deny spelled that way left the folder readable). A hard link to a file outside, made before the agent was confined (by another program, or while confinement was off), lets it write that file through the name it may write (measured; a confined agent cannot make one itself: `ln` is refused; #571). A `write` entry that is such a file (a second name, `st_nlink > 1`, read from the descriptor the walk resolved), or a save sibling it opens (`<file>.*`) that is one, refuses the start (`writable_has_links`). Accepted risk: such a link inside a *folder* the agent may write (its worktree, `~/.claude`) is not looked for, because the link must be made from outside confinement and scanning those folders at every start costs too much. Below it: no read of contents, metadata or extended attributes, no write, no unix-socket connection (Seatbelt checks a unix socket as `network-outbound`, not as a file, so a folder the agent cannot read still let it connect) and no socket bound (so an agent resumed before the node binds its control socket cannot bind it first). The folders above the home that the agent may write (a home under `/tmp`) are closed to renaming or removal, so the home cannot be moved out from under rules that name its path. Measured with real `sandbox-exec` for a home under `/tmp`: rename, writes to `publishers` and `manifests`, early bind, hard and symbolic links, a relative path, upper case, the `/System/Volumes/Data` firmlink, a copy-on-write clone (`cp -c`), a worktree or a writable folder swapped for a link into the home, and a job handed to launchd (`launchctl submit`/`bootstrap`/`load` are refused from a confined process; `launchctl asuser` stays confined) are all refused. Not measured yet: asking another unconfined program to act for the agent through Apple Events or LaunchServices (`osascript`, `open`); the profile starts from `(allow default)`, so these services are reachable unless a rule names them. Windows (measured 2026-11-14, #440; no code change was needed): the node's control pipe allows only its owner and SYSTEM (`OWNER_ONLY`, `D:P(A;;GA;;;OW)(A;;GA;;;SY)`, `agora-platform/src/windows.rs`), and a confined agent (ADR-0050) runs with a restricted token whose restricting SIDs are only its own agent SID, Everyone, Users and the logon SID, at Low integrity. Two separate checks refuse the open: the restricting-SID check finds no entry for any of them, and a Low process cannot write to the Medium pipe. ## Kill switch

Every client exposes "stop all agents" globally, per project, and per node. The node honors it even when
the instruction arrives without hub connectivity (local CLI).

## Implementation status: approvals (T1, T4)
`agora-node::approvals` enforces on the node: signature verified against keys the node already trusts, signed message bound to
node id, approval id and verdict (no replay on another node or request, no flipping deny to allow), 128-bit random single-use
ids, expiry, cancellation when an agent stops, and a policy that lists which actions need approval. The signature scheme sits
behind a `Verifier` trait; the scheme is ECDSA P-256 (ADR-0028, `P256Verifier`). Trusted device keys reach the node only through its owner:
`agora node trust DEVICE_ID PUBLIC_KEY_HEX` writes `<data>/trusted-devices` on the machine itself (read at start and again whenever the file changes, so trusting a browser never means restarting the node and stopping its agents; malformed
lines are skipped, never trusted), and no hub or client message can edit it. The web client keeps a non-extractable P-256 key in the browser (IndexedDB); its "This device" page shows the public key and the exact `agora node trust` command, and approvals are signed there (`apps/web/src/net/approval.ts`) and verified on the node. ADR-0061 (`agora-node::device_trust`, "Devices" in `docs/specs/protocol.md`, threats T20 and T21): `agora node enroll` and
`agora node trust --from-hub` show the hub's registered devices with fingerprints and trust them only on the owner's `y` at that
terminal (a non-interactive one is a no; `--yes` covers only the fingerprints given); a device already trusted can endorse another
(verified on the node: trusted signer, this machine in scope, at most 90 days, not revoked since, never longer than the signer's own
trust; renewed by use); a revocation signed by a trusted device, or `agora node untrust`, removes a device at once and is remembered in
`<data>/device-revocations` so an older endorsement cannot bring it back (also after the owner trusts it again); one dated ahead of the
node's clock is also kept in `<data>/device-revocations-ahead` so the owner's re-trust overrides it when the hub sends it again (ADR-0081); every endorsement and revocation applied or refused is
written to `<data>/device-trust.log`. The trusted-devices file stays owner-only (written beside itself and renamed).

### Signed grants for routed commands (ADR-0041)
`agora-node::grants` gates the commands a hub routes to the node (the uplink path only; the node's own control socket is never gated).
Policy line in `<data>/policy`: `signed_commands = agent.start, terminal.*, files.write` (exact names or a prefix ending in `*`; absent or
empty means none). A listed command with no live grant is refused with `approval.grant_required` and runs nothing. A grant is made by
`GrantCreate`, signed (ES256, same trusted devices as approvals) over `agora-grant-v1 NUL node_id NUL grant_id NUL scope NUL commands NUL
expires_at_ms`; `scope` is `node`, `agent:<id>` or `project:<id>`; it lasts at most 8 hours; the node keeps grants in memory only (a
restart ends them), refuses a grant id it has seen, a wrong signer, another node's grant and an expired one. `GrantList` and `GrantRevoke`
need no signature. Commands that name a worktree or open a new terminal (`files.write`, `worktree.*`, `terminal.open`) name no agent, so only
a `node` grant covers them. Recommended for a machine that is not a throwaway: `signed_commands = agent.start, terminal.input, files.write` (reading stays free). Typos in the line cannot widen anything: an unknown name simply matches no command. Tests: `crates/agora-node/src/grants.rs` and `crates/agora/tests/hub_dial.rs`.

### Launch options that skip permissions (ADR-0059, T15)
Policy line in `<data>/policy`: `skip_permissions = forbid | allow | confined_only` (absent: `allow`, the maintainer's default; any
other value counts as `forbid`). It is read when the node starts and never changes over the hub. `agora-node::launch_options` resolves a
start's option ids against the kind's manifest (unknown, repeated or more than 8: `protocol.invalid_message`) and refuses a
`skips_permissions` option the policy does not allow with `agent.option_forbidden` before any worktree, mesh endpoint or process
exists; `confined_only` allows it only when the node confines agents (`sandbox` not `off`) and can here. Through the hub, an
`AgentLaunch` with options is verified over `directory-action-v3` (the option ids are signed); a routed `AgentStart` with options is
refused at the uplink (`policy: signature`) whatever grant is live; the hub refuses to forward options to a node without the
capability `agent.launch_options`. Helpers (`agent_start`) are started through the supervisor's option-less calls, so they never
get one. The arguments are kept for the agent's whole life (crash restarts and resumes use them too); `AgentStarted` carries the ids
and `skips_permissions`, the hub keeps them in the snapshot (the badge) and writes an audit row `agent.launch_options` for every such
start, local ones included, besides the routed command's row (`AgentLaunch[skip-permissions]`). Tests:
`crates/agora-node/tests/launch_options.rs`, `agent_spawn.rs` (`a_helper_never_inherits_a_launch_option`),
`directory_authorization.rs`, `uplink_client.rs` and `router.rs` unit tests.

### Approvals: node wiring
Adapter approval requests enter the node's queue under a random node-minted id (the adapter's own id is only used to answer it),
are announced as `ApprovalRequested`, and wait. `approval.resolve` verifies the device signature on the node and relays the verdict
to the adapter, recording `ApprovalResolved` with the signer; requests that expire are answered as denied; a stopped or crashed
agent leaves nothing waiting. With no trusted device (the default until the owner runs `agora node trust`) every decision is
refused with `approval.signature_invalid`, so sensitive actions stay denied rather than open. Adapter usage and session reports
are written to the event log.

## Team mode (ADR-0049)
A hub may have several people with a role each (`owner`, `member`, `viewer`). The hub refuses a viewer's commands that change anything (`auth.forbidden`) and checks the role on every command, so a demotion or a removal takes effect on an open connection. This is the hub's own limit on its clients and not a security boundary: a compromised hub is still bounded only by the node's policy and signed grants (ADR-0020, ADR-0041). A member or viewer sees only the projects granted to them: the hub cuts their snapshot, forwards only their events, and refuses commands that do not name something in a granted project (`agora_hub::scope`). On the node, `device.<id>.projects = a, b` in `<data>/policy` limits what a trusted device may sign: grants only scoped to those projects (never `node`), and approvals only for agents of those projects; a device the file does not name is limited by nothing (today's behaviour), and a named one with no projects acts in none. The hub cannot change the file. When a node names any limited device and has no `signed_commands` line, it requires a grant for every command that changes something (`agent.start|stop|prompt|set_mode`, `terminal.open|input`, `files.write`, `worktree.create|remove`), so the limits bind those commands; a limited device can only sign project or agent grants, so whole-machine commands (`terminal.open`, `files.write`, `worktree.*`) stay the owner's. An owner who writes a `signed_commands` line decides the list. Without limited devices nothing changes. This binds only what is signed: the commands a node lists in `signed_commands` need a grant, so a member's browser device is limited by the node only for those commands (an owner who wants a member limited on the machine lists the commands there). Commands outside `signed_commands` still rely on the hub's role and project checks. The audit trail itself exists (`agora hub audit export`): every routed command, sign-in and change to the team is a row, kept by database triggers that refuse deletes and edits, so a client command cannot rewrite history; a compromised hub process with database access still can, so the trail is evidence about people, not about the hub.

Found by an independent audit after 0.2.0 and fixed: a passkey added by a member or viewer used to sign in as the owner (passkeys had no person, and a sign-in with one made an owner session). A passkey now belongs to the person whose session added it and signs in as that person (schema 8); removing a person removes their passkeys; the ids `owner` and `hub`, which the hub writes itself, can no longer be a person's (so no audit row can pose as the owner's); and starting an agent in an existing worktree is checked against the person's projects. Known and accepted: a member sees the machine-wide counts in a machine's resource events (agents running, terminals open, memory) for any machine that hosts one of their projects.

## Selected folders and portable identities (ADR-0052)

Directory inspection and launch are always authorized on the node by an exact-request trusted-device signature over
node, operation, path, kind, expected project, metadata/worktree option, changed-identity confirmation, nonce and expiry.
A generic start grant cannot substitute another path. Used nonces persist across restarts; malformed or full replay state
fails closed. See `specs/protocol.md` for the canonical encoding. A device limited to some projects (ADR-0049) may take
these actions only inside its projects, placed by the node's own records (folders launches confirmed and registered
checkouts, nearest wins; the session ledger for a resume), never by a folder's metadata, so a copied identity cannot move a
folder into its project; it can neither create nor change an identity, list the home folder or any folder outside its
projects, and the check runs after the signature so only a trusted device learns where a project is. A registered project
named in the request is resolved as the action resolves it (an id before a name; a name two projects share is refused).
Accepted (review of #478): the path is resolved for the check and again by the action, so anything that can write inside the
project, including the limited device's own agent, can swap a subfolder for a link to a folder elsewhere between the two. The
impact is bounded: for `list`, the names of the sub-folders of that other folder; for `inspect`, its project id, Git root and
branch; a launch still lands only in a folder whose identity is the project the device signed for (the launch checks it), so it
never starts an agent in another project. The local owner-only socket keeps its authority.


Folder listing (ADR-0053 `directory.list`) discloses **folder names only** (and whether each holds a `.git`), one folder per
call, at most 500, to the same exact-request owner signature (operation `list`, node and path bound, single-use nonce); a
device limited to projects never lists a machine. The node never lists a file, a link, a secret folder below the home folder
or its own folder (the same set a confined launch refuses), and refuses to list one of those when asked directly. The
decision is made on the folder the open handle holds: the path is opened once, the handle's own path must be the canonical
folder asked for, the secret-folder check runs on that path and the entries are read through that handle, so a folder
swapped for a link between two looks cannot show a secret folder (tested with a folder flipped against `~/.ssh`). The local
owner-only socket keeps its authority here as well.
The node resolves symlinks and re-inspects the canonical path/project immediately before launching. It preserves selected
user-owned folders on stop or failure. MCP files for direct L1 sessions live in separate session folders, accessible to that
agent's sandbox as read-only configuration; fixed-file-only MCP manifests require explicit worktree mode. Opt-in sandbox
policy still applies to the selected cwd. Sharing a folder deliberately shares its files; file leases cannot intercept an
agent's own shell writes, and the UI makes no per-agent attribution of a shared diff.

Repository metadata is untrusted data. It never enrolls a node, grants access, joins another owner's project or changes
device limits. It is a size-limited regular JSON file with a validated UUID. Previously confirmed path/ID bindings are
persisted and cannot silently switch after repository edits; an explicit signed owner confirmation is needed. Hub project
filters group confirmed logical IDs while preserving each machine and path; role/project filters still apply to workspace
snapshots, status events and file queries. Copying this metadata transfers identity, not source files or authorization.

Selected-directory review follow-up (#257): explicit worktree launch resolves the new root and walks the selected
relative directory without following restored symlinks. Missing directories are created only below that root; a
non-directory or symlink is refused before launch. Workspace diffs include an explicit selected-directory pathspec
even for an empty requested path, keeping parent-checkout changes outside the workspace review. Confinement tests
place a selected subdirectory outside the shared system temp folder and prove inside writes succeed while parent
checkout writes fail, in both directory and explicit-worktree modes. Explicit policy write allowances still apply.

## Known limit: certificates are not renewed (ADR-0085, Proposed)

Machine certificates and the hub's server certificate last 90 days (`DEVICE_CERT_DAYS`) and nothing renews them. A machine whose certificate
has ended is refused at its next connection (an open connection is not cut), and a hub that keeps running past the end of its own server
certificate is refused by every machine that dials it (it issues one at start). Both are proven with a few-second lifetime in
`crates/agora/tests/cert_lifetime.rs`. This is an availability limit, not a way in: an expired certificate is never accepted. Until renewal
is built the owner joins each machine again before day 90 and restarts the hub now and then; `agora doctor` (node `cert.pem`, hub
`server-cert.pem`) warns 30 days before and fails after the end, and `agora hub machines` notes a machine close to its end.

## Open gap: unix sockets under confinement

A confined agent (`sandbox = worktree`) can connect to any unix socket it can name. A tmux server socket or `SSH_AUTH_SOCK` lets it run a command or use
credentials outside the confinement. Landlock covers this only from ABI 9; Seatbelt needs an explicit rule. Tracked as L21 in
`docs/backlog/lan-test-findings.md`; `worktree-offline` on macOS already allows only the agent's own mesh socket.

## Hard links under confinement (#571)

A hard link made outside confinement (by another program, the user, or an agent that ran with `sandbox = off`) gives a file in a
place the agent may write a second name somewhere it may not. A confined agent cannot make such a link itself, but it can write
through one that exists: Seatbelt checks the path that was opened, and Windows confinement puts the agent's grant and the Low label
on the file object itself, which both names share.

- **Windows:** a start is refused (`writable_has_links`) when a regular file in the agent's worktree, or a write entry that is itself a
  file (a manifest's `~/.claude.json`), has more than one name, found by the walk that already checks every object before anything
  changes. `node_modules`, `target` and `.git` are not checked: package
  stores and git link there on purpose (real folders only: a file of such a name is checked). In three real pnpm checkouts, 36–87 % of the files were links into the pnpm store, all below
  `node_modules`, and none elsewhere. **Accepted risk:** while a confined agent runs, the store copies of those `node_modules` files
  carry its grant (they are the same file objects), so it could change those files in every pnpm project on the drive that
  links them (a store file had 10–23 names in the measured checkouts, #594). Also not seen: a link planted
  earlier by an unconfined actor (the user, another program, or an agent that ran with `sandbox = off`) below `node_modules`,
  `target` or `.git`, through which a later confined agent could write the file's other place. Closing that would mean
  not granting a store-linked `node_modules` at all. Windows confinement stays off by default (ADR-0050).
- **macOS (#592):** a write entry that is itself a file with more than one name (`st_nlink > 1`, read from the descriptor the
  #555 walk resolved) refuses the start (`writable_has_links`), and so does a save sibling such an entry opens (`<file>.*`, e.g. a
  `state.json.tmp` already there as a second name of another file; found in the #592 review, measured). Folders the agent may write (its worktree, `~/.claude`) are not
  scanned at every start: **accepted risk**, as the link must be made from outside confinement and the scan costs too much (T16).
- **Linux:** not measured yet (the control socket is a separate matter: T16, ADR-0082).
