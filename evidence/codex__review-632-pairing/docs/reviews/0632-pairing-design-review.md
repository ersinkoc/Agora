# PR #632: pairing design security review

Reviewed head: `87e595d7f8ef9a5d4cde490a29ad358cdc492167`.
Verdict: **DESIGN CHANGES NEEDED**, before implementation. No machine SAS grinding break is claimed.

## P2: unauthenticated browser replacement is not ownership-checked or churn-bounded

Section 6 replaces an existing pending browser request based only on its source address, without requiring that request's poll/continuation token. A second browser behind the same address can invalidate the first browser's pending sign-in. An address is a shared resource, not proof of ownership of a browser session. Replacements should require the existing pending request's capability token; an unrelated new request can instead be refused when its quota is occupied.

The concurrent caps (four globally/two per address) and three-minute lifetime do not themselves bound request creation or card/notification churn. The three/minute and twenty/ten-minute wording in section 7 is attached to the machine-session bullet; it must explicitly cover browser admissions/replacements too, with an additional global budget, before allocating state or sending notices. A per-request one-time card still permits repeated fresh cards. Replacement is not listed as a deny/mismatch/expiry, so those failure counters do not constrain this trace.

The executable design trace creates one legitimate pending browser request, followed by 10,000 same-address replacements: only one request remains pending, every stated concurrent cap is respected, no listed failure happens, but there are 10,001 notices and the legitimate poll token no longer names a pending request. This models the transitions permitted by the document, not an implemented server; if section 7 was intended to bound all request kinds, make that normative and retain the token ownership correction. Add bounded admission/replacement and polling rates, per address/prefix and globally, notification coalescing/cooldown, and token-authenticated continuation/cancellation.

The referenced existing `enroll::Lockout` stores one `(count, until)` behind a mutex, with no address argument. Its shared instance is hub-wide (`enroll.rs` documentation explicitly says so). Reusing it alone cannot deliver the stated per-address behavior and could accidentally lock fallback enrollment for unrelated users. Specify the keyed pairing counters, their retention bound and whether they are separate from fallback enrollment. This is an implementation prerequisite, not a claim that an unbuilt endpoint has already reused the wrong object.

## P2: the mandatory leaf-name check rejects the existing default LAN setup

Section 5 step 6b requires the dialed address to be one of the TLS leaf's names. Current `hub_run` uses `names=["localhost"]` unless `--name` is supplied (`crates/agora/src/hubcli.rs:162`); `Ca::issue_server` constructs SANs from only that list (`crates/agora-hub/src/ca.rs:139`). A default hub discovered or typed by its LAN IP therefore cannot pass the stated check, even after successful number comparison and approval.

Specify how advertised/dialed addresses get valid server certificate identities, or define an explicit post-comparison private-CA identity rule consistent with existing pinned behavior. Do not leave this to an implementer silently weakening verification, and do not call a default LAN install complete while it always fails. Include a normal default-hub LAN-address acceptance test plus wrong-leaf/wrong-CA controls.

The OpenSSL control generates a private fixture with exactly the default SAN shape, `DNS:localhost`. CA-chain verification succeeds and the localhost-name control succeeds; verifying the documentation-only LAN address `192.0.2.10` fails with IP-address mismatch. The fixture is generated by OpenSSL, not the repository CA library or an unbuilt pairing server; repository source establishes that its default SAN shape is the same. No network or real credentials are used.

## Machine exchange and requested open points

1. **Public hub nonce:** I did not find an offline nonce-grinding attack when every exchange is strictly one-shot, both sides use fresh 128-bit randomness, the commitments/challenges and TLS context are frozen, and retries create fresh sessions. Relaying the honest commitment hides the honest node nonce until the intermediary has fixed its challenge; substituting a separate node commitment fixes that node's nonce/CSR before the real hub's fresh challenge. This is a reasoning check, not a formal proof of a custom cryptographic protocol. The [ZRTP commitment discussion](https://www.rfc-editor.org/rfc/rfc6189.html#section-4.4.1.1) explains why preventing adaptive choices matters; it does not certify this different construction.
2. **Six digits:** approximately one in a million per correctly constrained comparison is not a bound on a whole pairing window or many sessions. State an explicit attempt budget and failure accounting across abort/reconnect/replacement, including the scope of address/global limits. [RFC 8628 section 5.1](https://www.rfc-editor.org/rfc/rfc8628.html#section-5.1) similarly relates short human codes to rate/attempt limits; its typed-code mechanism is not this SAS protocol.
3. **Leaf hash versus exporter:** prefer an explicit TLS session binding. [RFC 9266](https://www.rfc-editor.org/rfc/rfc9266.html#section-2) defines a 32-byte TLS exporter binding; current in-tree rustls exposes `Connection::export_keying_material` in `conn.rs`. Specify TLS 1.3 or the required TLS 1.2 extended-master-secret condition, label/context/length, and when the exporter is frozen. This needs no new crate. A certificate hash identifies an endpoint certificate rather than a unique TLS session; I have not shown that distinction alone breaks this design.
4. **Verifier:** accepting an untrusted CA during pairing must not mean accepting an invalid TLS handshake signature. Require proof of possession of the leaf key, reject a missing leaf/failed handshake, restrict the verifier to fresh pairing connections and messages, and perform the approved chain/identity validation before storing trust. Do not return unconditional assertions from TLS handshake-signature checks.
5. **State/identity:** make the existing one-connection/one-pairing statement an explicit transition table. The owning connection, commitment, leaf/exporter binding, nonce, CSR hash, node identity and deadline become immutable. A second request/challenge/reveal, replayed reveal, or another connection presenting the same `pair_id` must not replace state or gain authority. The pair id is a lookup key, not a bearer capability. Approve and deny are terminal and issue at most once, against the frozen tuple; reconnect does not reclaim it. These must have negative tests before code is integrated.
6. **Browser polling:** the poll capability needs explicit CSPRNG entropy (at least 128 bits), lifetime, one-time session delivery, no secrets in logs/URLs, invalidation on denial/close/expiry, and a trusted transport/session-cookie policy. Its displayed number is a request locator, never a password. An unauthenticated caller must not replace someone else's pending capability merely by sharing an address.
